Privacy

This page says what the site is built to do with your inventory, what checks it, and what the site cannot promise. Each statement names the check that backs it; the checks are tests in the repository, which run on every change.

Nothing leaves the browser

The assessment runs in your browser, compiled to WebAssembly from the same Go code as the shift2eu CLI. There is no server-side code: the site is static files, and no inventory, report or choice you make is sent anywhere. Three layers hold this.

Until shift2eu.com is on the HSTS preload list of shipping browsers, a first visit is at risk: HSTS on www.shift2eu.com protects only a browser that has already visited it over HTTPS. On a first visit, or a visit that starts at http://shift2eu.com (answered by the apex redirect's provider, which may send no HSTS), a network attacker can strip HTTPS and serve a look-alike page that sends your inventory away. To avoid it, type https://www.shift2eu.com yourself, or run the attested bundle locally (see Verify this site).

  1. The code sends nothing. The page's one script and the Go code that talks to the browser are held to a static rule that refuses every browser API that can send data or load a resource (fetch, XMLHttpRequest, WebSocket, beacons, WebRTC, workers, navigation), every way to reach another window (postMessage, opener, parent, top, BroadcastChannel, MessageChannel, window.name, message listeners) and every property name computed at run time that could hide one. Backed by the banned-API scan of the page script and of the glue's allow list of names (PRD #297, Trust, Layer 1).
  2. The browser refuses connections. Every page carries a Content Security Policy that refuses every network connection (connect-src 'none'), every image (img-src 'none'), every worker (worker-src 'none'), every form submission, every frame, inline script and every third-party resource. The scripts and the stylesheet are loaded with Subresource Integrity. Backed by the static test of each built page's policy and integrity values, and by the headless-browser smoke test, which tries to send and finds every attempt blocked (Layer 2).
  3. The files you load are the released ones. Each release builds the site reproducibly, attests the bundle and checks that the live site serves exactly the attested files. Backed by the reproducibility test and the release's live check (Layer 3); Verify this site shows how to check it yourself.

The site sets no cookies, stores nothing in your browser (no local storage, session storage or database), runs no analytics and loads nothing from a third party. Backed by the banned-API scan (no storage API), the policy test (no third-party source) and the static test of every loaded resource (Layers 1 and 2).

What the site cannot promise

  • The hosting provider, Scaleway, sees what any web server sees: your IP address, your user agent and the files you request. It sees nothing of your inventory, which never leaves your browser.
  • Browser extensions can read any page, this one included.
  • A released page served from a poisoned cache can stay in your browser's own cache for up to its max-age, 300 seconds, after the site is repaired. A page uploaded with a leaked deploy key sets its own caching, up to a year, and can register a service worker; both can outlast the repair in your browser, since the site cannot send Clear-Site-Data. The page script removes any service worker when a genuine page loads, which helps only visitors who load one.
  • The live checks compare the files in the attested manifests, the site's root and a few well-known service-worker paths. A look-alike page uploaded at a new path with a leaked key is not detected by them.
  • If you must not trust the host at all, run the attested bundle locally with any static file server: it runs unchanged on any origin (see Verify this site).

Technical note

  • The report is the one piece of markup the page inserts, rendered in Go by the HTML reporter, which writes only its own constant elements and every value as escaped text. The page inserts it in one place, through a Trusted Types policy (require-trusted-types-for 'script'). Not every browser enforces Trusted Types: in one that does not, that insertion rests on the reporter's escaping, pinned by a differential test against html/template and by a hostile golden, and on the Content Security Policy's ban on inline script, not on Trusted Types.
  • Go's wasm_exec.js is trusted as toolchain code, not scanned: the bundled file is byte for byte the one the building Go toolchain ships, which a test checks, and that toolchain is pinned by go.mod. The module script is not scanned either: it is one fixed template that carries only the encoded module, which a test checks.
  • The Content Security Policy does not govern navigation, WebRTC, DNS prefetch or messaging to another window (postMessage, opener, parent, top, BroadcastChannel, MessageChannel, window.name). The banned-API scan closes these gaps in the page's own code, and each page turns DNS prefetch off; the framing guard also sets window.opener to null as defence in depth.
  • One gap remains: the site cannot send Cross-Origin-Opener-Policy, so a page that opened this one keeps its handle to it. With that handle it can navigate the tab or post a message in, and read nothing; the page reads no message.
  • A meta Content Security Policy cannot carry frame-ancestors, so the page script stops, and says why, when another page frames it.

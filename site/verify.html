Verify this site

This site is shift2eu {{.Version}}. Every release publishes the site's bundle, attested by the release workflow, so you can check that what you run is what the release built. The release verification guide has the exact commands; this page summarises them.

Type https://www.shift2eu.com yourself rather than following an http:// link: on a first visit a network attacker can strip HTTPS and serve a look-alike page. The guide, served by GitHub, carries the same advice.

{{- if .HSTSWaived}}

HSTS is not in force for www.shift2eu.com: the maintainer waived it. Without HSTS the downgrade risk covers returning visitors too, not only a first visit, so type https://www.shift2eu.com every time, or run the attested bundle locally.

{{- end}}

Check the live site

  1. Note the version this page shows, {{.Version}}, and download that release's site bundle, shift2eu-site_<version>.tar.gz, from the repository's releases.
  2. Verify its attestation with the GitHub CLI: gh attestation verify on the bundle with --signer-workflow naming the release workflow, --source-ref refs/tags/<tag> and --deny-self-hosted-runners.
  3. Read manifest.json in the bundle, fetch each file it lists from https://www.shift2eu.com, and compare each file's SHA-256 with the manifest's.

The check is one point in time from one vantage point: the HTML is the root of trust and nothing pins it. A released page from a poisoned cache can stay in a browser's cache for up to its max-age after the site is repaired, while a page uploaded with a leaked key sets its own caching and can register a service worker, both of which can outlast the repair. A path outside the manifests is not checked.

Run the bundle yourself

The bundle runs unchanged on any origin. Extract the verified archive and serve its directory with any static file server on your own machine, then open it in your browser: you run exactly the attested files, and the host sees nothing.
